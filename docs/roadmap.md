# Roadmap

Status (2026-11-17): Phases 0 through 2h are built and independently verified; Phase 2h passed with 960 tests and no findings. Phase 2i ([phase-02i](phases/phase-02i-safe-store-startup-and-reads.md), safe store startup and reads) is specified with 76 given tests; implementation and verification are pending. The remaining [audit](audit.md) remediation phases below are planned before Stage 3.

Build one stage at a time and move on only when its test passes. Stage N is Phase N, split into lettered sub-phases (`1a`, `1b`) when it is too big; numbers are never reused.

**Build order:** 0 → 1 → 2a–2e → audit remediation 2f–2n → 3, then 4 once the shared Discord service exists, then 5 → 11. Phase 2o adds type checking once its dependency is approved. Stage 2 comes early because it unblocks the email service's Phase 3c; stage 3 needs no Discord, email or calendar, since it sends through a fake. No second HTTP client is enabled before 2f passes.

## Audit remediation before reminders

Use the [audit](audit.md) as the planning input. Its finding numbers below refer to that document. Keep the original audit unchanged as the record of the reviewed tree. Each row becomes its own spec, verification guide and given files, prepared one phase at a time against the preceding verified result. The rows describe acceptance behaviour, not ready-to-run coder assignments. No product feature from Stages 3–11 is included.

The order puts the approval boundary and unsafe stored text first, then concurrency and shared behaviour, then structural cleanup. Keep phases within the architect's limits: about 10 requirements, 3–5 public units, one migration and 30 given test functions, and about 300 implementation lines. Split a row further before specifying it if the concrete scope exceeds those limits; never combine rows just because they touch the same file.

### Decisions to settle while writing the specs

- **Reference limits and upgrades (2g, resolved Nov 17):** 512 code points per message ID and 2,048 per link; reject Cc, Cf, Zl and Zp. An invalid legacy reference blocks the upgrade without changing rows, reporting only ID and field. Repair requires a separate explicit action. The email contract and fake currently lack these bounds; matching work is documented in the email handoff. The existing 200-character retry-key rule stays separate.
- **IDs (finding 9, before Stage 3):** reconcile `AGENTS.md` with the existing committed row-number task and link IDs. State explicitly which future persistent rows use SQLite numbers and which externally keyed operations use `docket.ids.new_id()`. Update the rule and architecture together before a reminder spec introduces an ID. This plan does not change current IDs.
- **Tooling boundary (2m):** choose the repository tools path and packaging/import arrangement before moving files; keep product critical coverage and tooling coverage separately enforced. Do not simplify the report parsers and move them in the same phase.
- **Type checker (2o):** obtain the owner's choice of checker and dependency approval before specifying installation. No dependency is authorized by this roadmap.

Finding 7's architect template/linter split is deferred to the next spec-format change: separate template text from checks in `.claude/skills/phase-architect/phase_tools.py` then, with generator/linter regression checks. It is not a prerequisite for reminders. Until the spot-check runner is changed to mutate an isolated copy, verifier spot checks run only on a clean disposable checkout, since process termination can bypass restoration. Acceptance commands in specs remain executable code and require review.

All remediation uses synthetic data and fake services. Every bug fix gets a failing-first regression, all existing contracts remain covered, and each implementation phase ends with the normal progress entry, `check.py` success and independent verification. This roadmap update is architectural planning, not a completed implementation phase; it adds no coder progress entry or PASS claim for 2f onward.

## Manual checks

The owner runs these once, after the phase passes; no agent runs them.

### Intake cross-check with the email service (after Phase 2d)

Stage 2's test says the email service's requests work against the real app. Until the email service sends its token (its Phase 3c), this check sends the same requests by hand, with synthetic data and a throwaway data folder.

1. In one terminal, from `tasking`: `export DOCKET_DATA_DIR=$(mktemp -d)/data`, then `.venv/bin/docket clients add email` (it prints the token once and writes the Keychain item `client.email`; keep the token for step 2 and for the email service's own setup later), then `.venv/bin/docket serve`. It prints `Serving on http://127.0.0.1:8767`.
2. In a second terminal, `export T=<the token>` and send the email service's task request (the shape of `mailroom.tasks_app.task_payload`) twice:
   `curl -s -w ' %{http_code}\n' -H "Authorization: Bearer $T" -H 'Idempotency-Key: gmail:check/1' -H 'Content-Type: application/json' -d '{"source":"email","title":"Check intake","deadline":{"date":"2026-12-01","time":null,"time_zone":"America/New_York"},"provider":"gmail","message_id":"check/1","link":"https://mail.example/check/1"}' http://127.0.0.1:8767/tasks`
   The first answer is `{"id":"t1"} 201`, the second `{"id":"t1"} 200`.
3. Send a link (`mailroom.tasks_app.link_payload`): the same command with `-H 'Idempotency-Key: gmail:check/2'`, the body `{"source":"email","provider":"gmail","message_id":"check/2","link":"https://mail.example/check/2"}` and the URL `http://127.0.0.1:8767/tasks/t1/links`. The answer is `{"id":"<the link's id>"} 201`; sent again, the same id with `200`.
4. Without the `Authorization` header, step 2's command answers `{"error":"unauthorized"} 401`. This is what the email service gets today.
5. Stop the server (Ctrl-C). `DOCKET_DATA_DIR` still set, `.venv/bin/docket tasks list --all` needs `DOCKET_TIME_ZONE` (for example `America/New_York`) and shows `t1` "Check intake", due Dec 1 (17:00 New York time, the date-only default). Then delete the throwaway folder. Keep the Keychain item only if this token is the one the email service will use; otherwise issue the real one later with `--replace`.

## Deferred items

These are later decisions, not rejections.

- Two-way calendar sync (edits on your phone updating the task)
- Automatic time blocks for dated tasks (a work time exists only when you plan one)
- Work times that repeat every day, or more than one work time per task
- Writing undated tasks to a calendar or a task list
- Outlook or Apple as write targets
- Quiet hours and an urgent flag
- Per-task reminder schedules
- Auto-verifying that work was completed
- Shared or multi-user tasks
